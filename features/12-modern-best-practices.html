现代 API 与最佳实践 ​

这是什么 ​

这一章把三个「现代 Vue 写法」串进一个真实场景：

  1. useId（Vue 3.5）：在组件内生成稳定唯一 id，专治 label 的 for 与 input 的 id 对不上号的无障碍问题 —— 手写 id 容易重复，SSR 下 还会服务端/客户端不一致；useId 保证同一次渲染中唯一且两端一致。
  2. InjectionKey + provide/inject：用 Symbol 包装的 key 让 inject 拿到精确类型（不再是 unknown），也杜绝字符串 key 撞名。
  3. 组合式函数设计：把「状态 + 副作用 + 清理」打包成 useXxx()， 在组件里复用多次；用 hasInjectionContext()（Vue 3.5）在函数开头 判断是否真的处于 setup 上下文，把「误用时钩子静默失效」变成 一条清晰的警告。

核心 API 速览 ​

API用途关键点
const id = useId()生成组件内唯一 id绑到 <label :for> 与 <input :id>；每个字段各调一次
provide(key, value)向后代提供数据必须在 setup 同步阶段调用
const themeKey: InjectionKey<Theme> = Symbol('theme')类型安全的 keyinject(themeKey) 自动推导 Theme | undefined
hasInjectionContext()判断当前能否 inject / 注册钩子组合式函数健壮性兜底（3.5+）
onUnmounted(fn)卸载清理组合式函数注册的监听/定时器必须自己收尾

组合式函数的设计约定 ​

  • 命名：use 开头；输入：参数或 props；输出：refs + 操作函数。
  • 自清理：在函数内部注册 onUnmounted / onScopeDispose， 调用方零心智负担 —— 「谁注册的副作用，谁负责收尾」。
  • 可复用：同一组件复用 N 次 = N 份独立状态、N 份独立副作用 （本演示的两个计时器卡片）。
  • 防误用：上下文敏感的函数（内部要用 inject / 生命周期）先 hasInjectionContext() 判断，误用给出清晰警告而不是静默失效。

常见坑（真实踩坑记录） ​

  • label 关联靠手写 id：两个表单用了同一个 id="email"，点击 label 聚焦到错误的输入框；SSR 时服务端/客户端 id 不一致导致 hydration 警告。 useId 一并解决 —— 注意一个字段一个 id，不要复用同一个。
  • provide 写在事件回调里：provide / onMounted 必须在 setup 同步流程 中调用；写在按钮的 click 里只会有 "provide() can only be used inside setup()" 警告，数据根本没提供出去。
  • 组合式函数忘清理：mousemove 监听、setInterval 在组件卸载后仍在跑， 内存泄漏 + 后台报错。原则：谁注册，谁清理；验证方法就是反复挂载/ 卸载看 Console 日志是否成对出现。
  • inject 拿到 undefined 一头雾水：要么 provide 的组件不是祖先、 要么 provide 发生在回调里没生效。组合式函数里用 hasInjectionContext() 提前拦住「根本不在 setup 里」这种低级误用。
  • 字符串 key 撞名：provide('theme', ...) 和第三方库的 provide('theme') 会互相覆盖且没有类型；InjectionKey<Theme> 的 Symbol 全局唯一且带类型，一次解决两个问题。
