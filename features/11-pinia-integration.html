Pinia 状态管理（沙箱内集成） ​

这是什么 ​

Pinia 是 Vue 官方推荐的状态管理库。生产项目里它通过 app.use(pinia) 挂到应用上；本沙箱拿不到 createApp 入口，所以用 setActivePinia(createPinia()) 手动激活 —— 之后 defineStore 创建的仓库 在 useStore() 时会先尝试 inject 应用上注册的 pinia，失败后回落到 active pinia（Pinia 的内置兜底逻辑）。

ts
import { createPinia, defineStore, setActivePinia } from 'pinia'

// 沙箱专用引导：没有 app.use(pinia)，必须手动设置 active pinia
setActivePinia(createPinia())

const useCounterStore = defineStore('counter', {
  state: () => ({ count: 0 }),
  getters: { double: (state) => state.count * 2 },
  actions: { increment(step = 1) { this.count += step } },
})

本特性的 import-map.json：为什么 vue 和 pinia 必须同源 ​

本特性的文件列表里多了一个特殊文件 import-map.json（编辑器里被隐藏）， 它是沙箱的模块解析表 —— 与 Vue 官方 SFC Playground 的机制完全一致：

json
{
  "imports": {
    "vue": "https://cdn.jsdelivr.net/npm/@vue/runtime-dom@3.5.42/dist/runtime-dom.esm-browser.js",
    "pinia": "https://esm.sh/pinia@4.0.3?external=vue"
  }
}

原因：pinia 是从 esm.sh 加载的独立模块，它内部也要 import 'vue'。 默认情况下 esm.sh 会帮它解析成「esm.sh 自己的 vue」，与沙箱内置的 jsdelivr vue 构成两个不同的模块实例，页面里同时存在两个 Vue 运行时：

  • store 里的 ref/effect 与组件用的不是同一套响应式系统 → 改 state 视图不更新（响应式失效）；
  • 还可能伴随 "Invalid VNode type" 之类的诡异报错。

修复思路是让两边解析到同一个实例：

  • ?external=vue 告诉 esm.sh「不要帮我解析 vue，保留裸导入」；
  • 于是 pinia 里的 import "vue" 回到沙箱的 import map， 与应用代码解析到同一个 jsdelivr vue。

这也是真实项目的经典问题：monorepo 或多份打包产物里 vue 被装了两份， 症状一模一样（对应 pnpm 的 pnpm dedupe、bundler 的 resolve.alias）。

核心 API 速览 ​

API用途关键点
defineStore(id, { state, getters, actions })Options 式仓库定义state 必须是返回初始对象的函数
useCounterStore()拿到仓库实例是 reactive 代理，模板里可直接用
storeToRefs(store)解构 state/getters 并保持响应式actions 是函数，直接 store.xxx() 调用
store.$patch({...})批量修改（对象形式）适合一次改多个字段
store.$patch((s) => {...})批量修改（函数形式）适合基于现值的修改（数组 push 等），多次变更合并为一次通知
store.$reset()恢复初始 stateOptions 式仓库专属
store.$subscribe(fn)订阅任意 state 变化常用于持久化 / 埋点（参考答案演示）

常见坑（真实踩坑记录） ​

  • 忘记 setActivePinia：报 "getActivePinia was called with no active Pinia"。沙箱 / 测试环境（vitest 单测同理）没有 app.use(pinia)， 必须手动激活，而且要在 defineStore / useStore 之前。
  • 双 Vue 实例 → 响应式静默失效：import map 里 vue 与 pinia 的依赖 版本不一致时页面不报错，但 state 改了视图不动 —— 最阴险的一类 bug。 自检方法：console.log(useStore().$state) 有值但不刷新，基本就是双实例。
  • 解构丢响应式：const { count } = store 拿到的是当时的快照数字， 不会随 store 更新；必须 const { count } = storeToRefs(store)。 actions 直接解构没问题（函数不依赖响应式包装）。
  • getter 里拿不到 this：箭头函数 getter (state) => ... 只能看到 state；要访问其他 getter 就写成普通方法用 this，并且显式标注返回类型。
  • $reset 是 Options 仓库专属：setup 式 defineStore（传入函数的那种） 没有 $reset，需要自己写 reset action。
  • $patch 函数形式才是数组的好姿势：直接 state.list.push(x) 也行 （Pinia 允许直接改 state），但 $patch 函数形式能把多次变更合并成 一次通知，devtools 里的记录也更干净。
